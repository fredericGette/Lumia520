## Qci2c8930.sys

I²C controller driver for the QUP (Qualcomm Universal Peripheral) cores of the MSM8930 (Qualcomm KMDF driver, PDB `P:\I2C\rel\8.2.1\arm\Release\qci2c8930.pdb`).  
It's an SPB controller driver built on the SPB framework extension (SpbCx). It exposes no IOCTL of its own: SpbCx handles the requests of the peripheral drivers (`IRP_MJ_READ`, `IRP_MJ_WRITE`, `IOCTL_SPB_EXECUTE_SEQUENCE`, lock/unlock) and calls the driver's `EvtSpbIoRead` / `EvtSpbIoWrite` / `EvtSpbIoSequence` callbacks. The driver then programs the QUP registers directly (`MmMapIoSpace` of the memory resource), in FIFO or block mode, and completes the transfer from its interrupt DPC.  
It serves the 3 I²C buses of the Lumia 520 (`QCOM0180`), whose GSBI blocks are set to I²C mode by [qcgsbi8930.sys](./qcgsbi8930.md) beforehand. The bus clients are the touch screen and the Nokia sensors, and [acpiex.sys](./acpiex.md) for the `GenericSerialBus` operation regions on `\_SB.IC12` (see [Lumia 520 ACPI nodes](#lumia-520-acpi-nodes)).  
Only 7-bit addressing and speeds up to 400 kHz are supported. The QUP source clock is assumed to be 24 MHz.

There's no named `\Device\` object and no symbolic link: peripheral drivers open the controller through `\Device\RESOURCE_HUB\<connection id>` (see [acpiex.sys](./acpiex.md#opening-a-connection-deviceresource_hubid)).

Registries of the driver:  
`HKEY_LOCAL_MACHINE\SYSTEM\ControlSet001\services\qci2c8930`  
`HKEY_LOCAL_MACHINE\SYSTEM\ControlSet001\Enum\ACPI\QCOM0180\3`, `…\9`, `…\C`  

There's no parameters in the registry.

GUID of the ETW provider (WPP control GUID, registered with `EtwRegisterClassicProvider`):  
`{EF49A24A-40CD-46D0-8A8A-3623B7A18969}`

It communicates with the following devices:  
| Device | Driver | Comment |
|--------|--------|---------|
| SpbCx (class extension) | spbcx.sys | Bound through `WdfVersionBindClass`. Every request goes through it |
| `\Device\RESOURCE_HUB` | [acpiex.sys](./acpiex.md) | Indirectly: `SpbTargetGetConnectionParameters` returns the `I2cSerialBus` descriptor of the connection, see [Target connect](#target-connect) |
| QUP registers (memory resource) | — | Mapped with `MmMapIoSpace`, see [QUP registers](#qup-registers) |

Pool tag: `qic1` (`WDF_DRIVER_CONFIG.DriverPoolTag`).

> [!NOTE]
> The surprise-removal callback (sub_401DB4) calls `WdfVerifierKeBugCheck(0x14E, 0x51696330 'Qic0', 0, …)`: removing the device crashes the phone (same behaviour as qcgsbi8930.sys, qcabd8930.sys, qcpmic8930.sys…).

### Device setup

`EvtDriverDeviceAdd` (0x4012AC):
- `SpbDeviceInitConfig`, then PnP/power callbacks: `EvtDevicePrepareHardware` (sub_401BA4), `EvtDeviceReleaseHardware` (sub_401D04), `EvtDeviceD0Entry` (sub_401DF0), `EvtDeviceD0Exit` (sub_401E98), `EvtDeviceSelfManagedIoInit` (sub_401F30), `EvtDeviceSelfManagedIoCleanup` (sub_402024), `EvtDeviceSurpriseRemoval` (sub_401DB4).
- `WdfDeviceCreate` with the context `PBC_DEVICE` (120 bytes, see below).
- `WdfDeviceSetStaticStopRemove(device, FALSE)`: the device can't be stopped or removed.
- `WdfDeviceSetDeviceState`: `NotDisableable` = `WdfFalse`, the other fields `WdfUseDefault`.
- `SpbDeviceInitialize` with `SPB_CONTROLLER_CONFIG`: `ControllerDispatchType` = sequential, `PowerManaged` = `WdfTrue`, `EvtSpbTargetConnect` (sub_402130), `EvtSpbIoRead` (sub_402240), `EvtSpbIoWrite` (sub_4022B8), `EvtSpbIoSequence` (sub_402330). There's no `EvtSpbTargetDisconnect`, no `EvtSpbControllerLock` / `Unlock` and no `EvtSpbControllerIoOther`, so SpbCx rejects every other IOCTL.
- `SpbControllerSetTargetAttributes` (context `PBC_TARGET`, 44 bytes) and `SpbControllerSetRequestAttributes` (context `PBC_REQUEST`, 88 bytes).
- `WdfInterruptCreate`: ISR sub_4025E0, DPC sub_402798, with a WDF spin lock. Handle in `PBC_DEVICE+0x18`.
- 2 WDF timers, both one-shot: `+0x44` "delay" timer (sub_403488) and `+0x48` "cancel" timer (sub_40373C). 2 more spin locks: `+0x3C` (transfer lock) and `+0x40` (request cancel flag).
- `WdfDeviceAssignS0IdleSettings`: `IdleCannotWakeFromS0`, DxState = `PowerDeviceD3`, IdleTimeout = 2000 ms, `IdleAllowUserControl`, Enabled = `WdfUseDefault`, IdleTimeoutType = `SystemManagedIdleTimeoutWithHint`.

PnP sequence:
1. `EvtDevicePrepareHardware` maps the first `CmResourceTypeMemory` resource (`MmMapIoSpace(…, MmNonCached)`; 0x800 bytes on the Lumia 520). No memory resource or a failed mapping → `STATUS_INSUFFICIENT_RESOURCES` (0xC000009A). The interrupt resource is handled by WDF.
2. `EvtDeviceSelfManagedIoInit` registers `PoRegisterPowerSettingCallback` on `GUID_MONITOR_POWER_ON` (sub_403CA8), see [Idle timeout](#idle-timeout).
3. `EvtDeviceD0Entry`: on the first D0 entry after start only, writes 1 to `QUP_SW_RESET`.
4. `EvtDeviceD0Exit` (sub_4049FC): if the QUP is initialised, writes 1 to `QUP_SW_RESET` and clears the "initialised" flag. So the core is reset each time the device goes to D3 (idle), and is reinitialised at the next request.
5. `EvtDeviceSelfManagedIoCleanup` unregisters the power setting callback. `EvtDeviceReleaseHardware` unmaps the registers.

### Idle timeout

The power setting callback (sub_403CA8) is registered for `GUID_MONITOR_POWER_ON`:  
`{02731015-4510-4526-99E6-E5A17EBD1AEA}`

At each notification it calls `WdfDeviceAssignS0IdleSettings` again with the same settings, except the idle timeout:  
| Monitor | Idle timeout |
|---------|--------------|
| Off (value 0) | 50 ms |
| On | 2000 ms |

### Target connect

`EvtSpbTargetConnect` (sub_402130) calls `SpbTargetGetConnectionParameters`. Its `ConnectionParameters` is the output buffer of `IOCTL_RH_QUERY_CONNECTION_PROPERTIES` (see [acpiex.sys](./acpiex.md#ioctl-0x2ac000--ioctl_rh_query_connection_properties)). `sub_40299C` parses it:  
| Bytes | Comment |
|-------|---------|
| 00-03 | Version (not checked) |
| 04-07 | PropertiesLength, must be ≥ 4, otherwise `STATUS_INVALID_PARAMETER` (0xC000000D) |
| 08 | 0x8E, Serial Bus Connection descriptor (not checked) |
| 0D | Serial bus type, must be 1 (I²C), otherwise `STATUS_INVALID_PARAMETER` |
| 0E-0F | Type-specific flags. Bit 0 (10-bit addressing) is **ignored**: the address is always sent as 7 bits |
| 12-13 | Type data length (6 without vendor data) |
| 14-17 | Connection speed in Hz, must be ≤ 400000 (0x61A80), otherwise `STATUS_NOT_SUPPORTED` (0xC00000BB) |
| 18-19 | Slave address |
| 1A-1D | Vendor data, used if type data length ≥ 10: extra timeout in µs (minimum and default 1000) |
| 1E-21 | Vendor data, used if type data length ≥ 14: bit 0 = "register restart" flag, see [Large reads](#large-reads) |

Target context `PBC_TARGET`:  
| Offset | Size | Comment |
|--------|------|---------|
| 0x00 | 4 | SPBTARGET |
| 0x04 | 4 | Slave address |
| 0x08 | 4 | Value written to `I2C_MASTER_CLK_CTL`: FS divider = 24000000 / (2 × speed) − 3 (HS divider 0) |
| 0x0C | 4 | Speed (Hz) |
| 0x10 | 4 | Byte time (µs) = 9000000 / speed + 1 |
| 0x14 | 4 | Bit time (µs) = byte time / 9 + 1 |
| 0x18 | 4 | Extra timeout (µs), vendor data or 1000 |
| 0x1C | 4 | Cancel timeout (µs) = (byte time + extra timeout) × 256 |
| 0x20 | 4 | "Register restart" flag (vendor data) |
| 0x24 | 4 | Request in progress on this target |
| 0x28 | 1 | 2-byte register address captured from the previous write |

Lumia 520 values: all the declared connections are 400 kHz without vendor data, so FS divider = 27 (0x1B), byte time = 23 µs, bit time = 3 µs, cancel timeout = (23 + 1000) × 256 = 261888 µs.

### Transfers

`EvtSpbIoRead` / `EvtSpbIoWrite` both call sub_402BC0, `EvtSpbIoSequence` is sub_402330. Both:
1. Read `SpbRequestGetParameters` into the request context (type, position, transfer count).
2. Initialise the QUP if needed (sub_40492C, see [Initialisation](#initialisation)). On failure, the status is returned.
3. Fail with `STATUS_UNSUCCESSFUL` (0xC0000001) if `I2C_MASTER_STATUS` bit 8 (bus active) is set.
4. Prepare the transfer (sub_4030DC): `SpbRequestGetTransferParameters`, map the MDL (`MmMapLockedPagesSpecifyCache`), save direction, length and `DelayInUs`.
5. Under the transfer lock, fail with `STATUS_UNSUCCESSFUL` if another target owns the controller or the target already has a request. Then start the transfer (sub_403334).

Sequences (sub_402EB0) are checked before step 4. Only one read is allowed, and it must be the last transfer; any number of writes can precede it. A read in another position, a read longer than 0xFFFF bytes, or more than 0xFFFF output tags → `STATUS_NOT_SUPPORTED` (0xC00000BB). The output tag count is the sum of (length + 1) of the writes, rounded up to an even number, plus 2 for the read.

Start of a transfer (sub_403334):
1. If the transfer has a `DelayInUs`, start the "delay" timer for this delay and return. The timer callback starts the transfer.
2. `WdfRequestMarkCancelableEx` (cancel routine sub_403628).
3. Sequence: block mode for both FIFOs (sub_404E14), `QUP_MX_OUTPUT_CNT` = tag count, `QUP_MX_INPUT_CNT` = read length, state RUN → PAUSE, `I2C_MASTER_CLK_CTL` = divider of the target. The output FIFO is then filled from the interrupt.
4. Single read or write (sub_40518C): the mode depends on the length (see below). Then the output FIFO is filled immediately (FIFO mode) or after the state change to RUN (block mode).

| Direction | FIFO mode | Block mode |
|-----------|-----------|------------|
| Write | length < output FIFO size / 2: `QUP_MX_WRITE_CNT` = length + 1 | otherwise: `QUP_IO_MODES` bit 10, `QUP_MX_OUTPUT_CNT` = length + 1 |
| Read | length ≤ input FIFO size / 2: `QUP_MX_READ_CNT` = length | otherwise: `QUP_IO_MODES` bit 12, `QUP_MX_INPUT_CNT` = min(length, 256) |

For a read, `QUP_MX_WRITE_CNT` is 2 (START + address, REC) or 5 (with a register restart, see below).

The output FIFO (`QUP_OUTPUT_FIFO`, 0x110) is written in 32-bit words that each hold two 16-bit tags, low half first. Each tag is `(tag << 8) | byte`:  
| Tag | Byte | Comment |
|-----|------|---------|
| 1 | (address << 1) \| R/W | START: 0 = write, 1 = read |
| 2 | data | DATA |
| 3 | data | DATA, then STOP (last byte of the transfer) |
| 4 | count | REC: read *count* bytes (0 = 256) |

The input FIFO (`QUP_INPUT_FIFO`, 0x218) is read in 32-bit words of two 16-bit entries (data byte, tag). A tag of 7 completes the request with `STATUS_NO_SUCH_DEVICE` and resets the QUP (sub_40590C).

#### Large reads

When the target has the "register restart" vendor flag, a write of at least 2 bytes followed by a read (sequence, or a locked write + read) copies the last 2 bytes written into the request (sub_403B90). During the read, at each 256-byte boundary, the driver sends again START (write), the 2 bytes (the second one incremented by 1 each time), then START (read) and REC (sub_404CB0). This presumably lets the driver read more than 256 bytes from a device whose register address doesn't auto-increment across the QUP's 256-byte REC limit ? None of the Lumia 520 connections sets this flag.

### Interrupt

ISR (sub_4025E0):
1. Accumulates `QUP_OPERATIONAL` & 0x3F00, `I2C_MASTER_STATUS` & 0x38000FC and `QUP_ERROR_FLAGS` & 0x7C (sub_403F4C).
2. If `I2C_MASTER_STATUS` bit 3 (NACK) is set, it sets the state to PAUSE and computes the number of bytes transferred (sub_403874).
3. Acknowledges the flags (sub_404084): writes `QUP_OPERATIONAL` & 0x300, `I2C_MASTER_STATUS` & 0x38000FC and `QUP_ERROR_FLAGS` & 0x7C back.
4. If one of them was set, it queues the DPC and claims the interrupt. Otherwise it increments the unclaimed counter.

> [!NOTE]
> After more than 5 consecutive unclaimed interrupts, the ISR calls `WdfVerifierKeBugCheck(0xF2 HARDWARE_INTERRUPT_STORM, QUP_OPERATIONAL, I2C_MASTER_STATUS, QUP_ERROR_FLAGS, QUP_STATE)`.

The DPC (sub_402798) handles the request of the target that owns the controller (sub_40415C). It refills the output FIFO or empties the input FIFO, moves to the next transfer of a sequence, or completes the request. Status mapping:  
| Condition | Status |
|-----------|--------|
| `I2C_MASTER_STATUS` bit 3 (NACK), no byte transferred | `STATUS_NO_SUCH_DEVICE` (0xC000000E) |
| `I2C_MASTER_STATUS` bit 3 (NACK) after some bytes | Success, Information = bytes transferred before the NACK |
| `I2C_MASTER_STATUS` bits 2 or 4, or bit 24 | `STATUS_NO_SUCH_DEVICE` (0xC000000E) |
| `I2C_MASTER_STATUS` bits 5, 23 or 25 | `STATUS_INVALID_DEVICE_STATE` (0xC0000184), and the QUP is reset and reinitialised |
| `QUP_ERROR_FLAGS` & 0x7C (FIFO over/under-run ?) | `STATUS_BUFFER_OVERFLOW` (0x80000005) |
| Bus still active (`I2C_MASTER_STATUS` bit 8) after 2 × (byte time + extra timeout), polled every 2 × bit time | `STATUS_BUS_RESET` (0x8000001D) |

At the end of a request (sub_405D38), the driver waits for the bus to become idle and sets the state to RESET. It releases the controller if the request was a sequence or a `Single` read/write, then completes it with `SpbRequestComplete`. Information = total bytes transferred.

Cancellation: the cancel routine (sub_403628) only sets a flag and starts the "cancel" timer for the cancel timeout of the target (~262 ms on the Lumia 520). The timer callback (sub_40373C) stops the transfer and completes the request with `STATUS_CANCELLED` (0xC0000120).

> [!NOTE]
> There's no watchdog on a transfer itself. If the QUP never raises an interrupt, the request stays pending until it's cancelled.

### Initialisation

sub_40492C runs before each request when the "initialised" flag (`+0x71`) is clear. It writes:  
| Register | Value | Comment |
|----------|-------|---------|
| `QUP_SW_RESET` (0x0C) | 1 | Reset of the core |
| `QUP_CONFIG` (0x00) | 0x20F | N = 15 (16-bit words), mini-core = 2 (I²C master) |
| `QUP_IO_MODES` (0x08) | 0xC000 | Pack / unpack enabled, FIFO mode |
| `QUP_ERROR_FLAGS_EN` (0x20) | 0x7C | All error interrupts enabled |
| 0x10 | 0 | ? |

Then it checks that `QUP_STATE` bit 4 is set (otherwise `STATUS_DEVICE_CONFIGURATION_ERROR`, 0xC0000182) and reads the FIFO and block sizes from `QUP_IO_MODES` (sub_404790). A size field of 0 means 4 bytes, otherwise 16 × the field. FIFO size = block size × (2 << the FIFO size field).

State changes (sub_404578) wait up to ~1000 µs for `QUP_STATE` bit 2 (valid) before and after writing the state (bits 1:0: 0 = RESET, 1 = RUN, 3 = PAUSE). They return `STATUS_DEVICE_CONFIGURATION_ERROR` (0xC0000182) on a timeout and `STATUS_UNSUCCESSFUL` if the state read back differs.

### IOCTL 0x41808 — IOCTL_SPB_EXECUTE_SEQUENCE

This IOCTL is processed by SpbCx for Qci2c8930.sys, which receives it through `EvtSpbIoSequence` (sub_402330)  

| Property | Value |
|----------|-------|
| Device | 0x4 (FILE_DEVICE_CONTROLLER) |
| Function | 0x602 (1538) |
| Access | FILE_ANY_ACCESS |
| Method | METHOD_BUFFERED |

| Name | InputBuffer size | OutputBuffer Size |
|------|------------------|-------------------|
| IOCTL_SPB_EXECUTE_SEQUENCE | `SPB_TRANSFER_LIST` | 0 |

The transfer list is parsed and its buffers are captured by SpbCx (layout in [qcabd8930.sys](./qcabd8930.md#ioctl-0x41808--ioctl_spb_execute_sequence)). The driver reads it only through `SpbRequestGetTransferParameters`. Restrictions: writes followed by at most one read, which must be last (see [Transfers](#transfers)). Each transfer's `DelayInUs` is applied before the transfer starts. For the first transfer it's a timer, for the next ones `KeStallExecutionProcessor` in the DPC (sub_405800).

The controller lock IOCTLs (`IOCTL_SPB_LOCK_CONTROLLER` 0x41800, `IOCTL_SPB_UNLOCK_CONTROLLER` 0x41804) are handled by SpbCx alone (no lock callbacks). The reads and writes in between reach the driver with a position other than `Single`, and the driver then keeps the controller reserved for that target.
